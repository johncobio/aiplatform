# V6 engine comparison — 2026-09-16

**Question:** same model, same node, same load: how does the repo's builtin
service (FastAPI + llama-cpp-python, portable build) compare with the upstream
llama.cpp server (`ghcr.io/ggml-org/llama.cpp:server-v0.4.1`) deployed through
the same chart with `engine: llamacpp-server`?

**Setup:** kind, 4 vCPU / 4 GB VM. Qwen2.5-0.5B-Instruct Q4_K_M, context 4096,
2 threads, `cpu: 2`, `memory: 1Gi`, `max_tokens: 32`, k6 via ingress-nginx.
One replica each, never both running at once. Builtin numbers are the V5
`steady1`/`steady2` runs (staging); upstream numbers are `qwen1`/`qwen2` (dev).
`-np 2` (two parallel slots) for the upstream server.

## Results

| Engine | VUs | Throughput | Median | P95 | P99 | Tokens/s total | Per-request tok/s (median) | Pod RSS |
|--------|-----|------------|--------|-----|-----|----------------|----------------------------|---------|
| builtin (llm-service) | 1 | 0.524 req/s | 1.91 s | 2.17 s | 2.26 s | 16.4 | 16.6 | ~650 Mi |
| llamacpp-server | 1 | **1.511 req/s** | **0.66 s** | 0.80 s | 0.95 s | **47.6** | **47.9** | 792 Mi |
| builtin (llm-service) | 2 | 0.557 req/s | 3.57 s | 3.94 s | 4.39 s | 17.6 | 8.8 | |
| llamacpp-server | 2 | 1.448 req/s | 1.35 s | 1.75 s | 1.92 s | 45.9 | 23.6 | |

0.00 % failures in all four runs (63, 182, 68, 174 requests).

## Observations

- **The upstream server is 2.9× faster on the same model and cores.** The
  builtin image compiles llama.cpp with `GGML_NATIVE=OFF` for portability
  (V1 decision) and therefore misses the ARM dot-product/int8 kernels; the
  upstream image ships optimised builds. Python request handling adds little
  by comparison (the builtin's own tracing showed generation at 98 % of
  request time). Follow-up queued: build the builtin image per-architecture
  with native kernels in CI and re-measure.
- **Concurrency does not add throughput on 2 cores for either engine**
  (1.51 → 1.45 req/s; 0.52 → 0.56 req/s). The upstream server's parallel
  slots split the same compute, halving per-request speed (47.9 → 23.6 tok/s)
  while keeping the median latency far below the builtin's serialised queue.
- **The metrics contract held.** With zero dashboard changes, the upstream
  engine reports pending requests (`llamacpp:requests_processing +
  requests_deferred`), token rates and per-request speed
  (`llamacpp:predicted_tokens_seconds`) through the `aiplatform:*` rules; the
  HPA read `llm_pending_requests` for it immediately. Request rate and P95
  for this engine come from ingress-nginx, because llama.cpp server exposes no
  latency histogram. `scripts/check_dashboard.py`: 0 problems for
  `environment=dev workload=qwen-server` (engine-specific panels excluded).
- **A no-code workload is real.** `services/qwen-server/aiplatform.yaml` is
  the entire deliverable: 1.1 s redeploy through the kind target once the
  model was cached.
- **vLLM** renders with GPU resources, model args and the HF token secret
  (`scripts/check_chart.sh`); it cannot run on this laptop and is deferred to
  the AWS GPU node group. Its metrics are already mapped in the rules.
