# 0005 — Local Kubernetes (kind) with a Helm chart before EKS

2026-09-16 · Accepted

## Context

The roadmap puts EKS in V2, but the owner wants to defer all AWS spend until
the platform is complete locally. EKS costs ≈ $73/month for the control plane
alone, and iterating on Helm charts, GitOps and observability against it would
burn money on mistakes that a laptop can absorb for free.

## Decision

- Add a `kind` deployment target (kind = Kubernetes in Docker) driven by a
  Helm chart `deploy/helm/llm-workload`. The chart is the contract; the EKS
  target later reuses it unchanged, only the image registry and ingress class
  differ.
- `aiplatform cluster up|down|status` creates a single-node kind cluster with
  ingress-nginx (host ports 80/443) and metrics-server (for HPA).
- Workloads are reachable at `http://<name>.<env>.127.0.0.1.nip.io`
  (nip.io resolves to 127.0.0.1), the local stand-in for a real DNS name on
  an AWS load balancer.
- Images are side-loaded with `kind load docker-image`; there is no local
  registry to run. The EKS target pushes to ECR instead.
- One namespace per environment: `aiplatform-<env>`. Environment overrides
  live in `deploy/environments/<env>/values.yaml`; workload-specific values are
  generated by the CLI from `aiplatform.yaml`.
- Rollback uses Helm's release history (`helm rollback`), so the platform does
  not reinvent what the tool already provides.

## Consequences

- V2 (Kubernetes/Helm), V3 (Argo CD), V4 (Prometheus/Grafana/OTel) and V5
  (autoscaling, load tests) can all be built and measured locally.
- The model cache is a ReadWriteOnce PersistentVolumeClaim. On a single kind
  node every replica can mount it; on EKS with EBS that is not true. The EKS
  phase must decide between baking the model into the image, an S3 init
  download, or EFS. Recorded in `TODO.md`.
- The laptop (8 GB) limits how many replicas and add-ons can run at once;
  measurements taken on kind are relative, not production numbers.
